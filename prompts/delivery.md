# 실제 증거로 산출물 작성

이 프롬프트는 산출물 작성 단계에서 사용한다. 운영·승인·시간·검증 규칙은 [AGENTS.md](../AGENTS.md)를 따른다. 최초 경로 연결은 [setup.md](setup.md)의 책임이며 여기서 과제 환경을 재설정하지 않는다.

새 세션이라면 setup의 재개 순서로 기존 기록과 승인 상태를 먼저 확인하고 이어간다. 각 산출물 작업 시작·종료와 검증 후 경과·남은 시간을 확인해 최종 검증·제출 여유를 확보한다. 긴 작업은 착수 전에 완료 기준·시간 상한을 계획에 기록한다. 원래 시작·마감 시각을 유지하고 시간 예산을 초기화하지 않는다. 시간 확인이 안 되면 현재 남은 시간만 사용자에게 확인해 progress에 기록한다. 135분 이후 새 확장 금지는 운영 규칙이며 자동 타이머에 의한 강제 중단을 뜻하지 않는다.

## 입력과 확인

1. 확인된 TASK_ROOT에서 과제의 최신 요구 산출물·제출 형식·경로·마감·제출 방법·시험 규정을 읽는다. 이전에 확인한 내용과 달라졌으면 변경과 영향을 알린다. 필수 자료가 없거나 충돌이 해결되지 않았다면 해당 산출물·제출을 임의로 가정하지 않는다.
2. 실제 코드와 기존 과제 문서, 승인된 implementation-plan, findings, progress를 읽는다. 기본 경로는 AGENTS.md의 작업 문서 표를 따르되 setup에서 재사용하기로 매핑한 문서가 우선이다. 계획은 구현 증거가 아니며, 진행 기록과 코드가 다르면 실제 상태를 확인해 구분한다.
3. 요구 산출물별로 필요한 근거를 연결한다. 테스트 기록의 검사 대상·시각·명령·기대/실제 결과를 확인한다. 코드가 마지막 검사 이후 바뀌었다면 영향을 확인하고 필요한 재검증을 수행하거나 미검증으로 표시한다.

## 작성 절차

| 산출물에 반영할 내용 | 근거 | 작성 규칙 |
| --- | --- | --- |
| 문제 정의·대상·성공 기준 | 과제 명세, 승인 계획, findings | 승인된 방향과 평가 기준을 설명 |
| 선택 이유·제외 범위 | 승인된 대안 비교와 결정 기록 | 사용자 결정과 에이전트 판단을 구분 |
| 실제 구현 내용 | 코드·변경 파일·실행 상태 | 계획만 있고 없는 기능을 구현했다고 쓰지 않음 |
| 실행 방법 | 과제의 실제 환경·설정·확인한 실행 명령 | 작업 디렉터리·필수 설정을 설명. 실행하지 않았다면 미실행 표시. 비밀값은 넣지 않음 |
| 검증 결과 | progress의 명령/시나리오·기대/실제 결과·검사 범위 | 통과·실패·미검증을 구분. 없는 성능·수치·테스트 결과를 만들지 않음 |
| 한계·다음 단계 | 미구현·실패·미검증·보류 기록 | 제출 시점의 제약을 명시하고 제안을 완료 기능처럼 쓰지 않음 |

과제가 요구하는 문서·발표·데모 설명·파일 형식에 맞춰 위 내용을 배치한다. 과제에서 요구하지 않는 산출물을 관성적으로 추가하지 않는다. 기존 README와 산출물은 먼저 읽고 필요한 부분만 보완하며 덮어쓰지 않는다. 새 파일 경로가 기존 파일과 충돌하면 내용을 확인하고 안전한 보완 방법을 결정한다.

작성 중 제품 변경이 필요하면 개발자→검증자로 돌아가 변경과 검사 결과를 progress에 남긴다. 승인 범위를 바꾸면 재승인받는다. 135분 이후 새 확장을 시작하지 않는다.

## 기능 사용 안내

사용자가 요청한 기능 설명서는 실제 코드·화면·검사 결과에 맞춰 작성한다. 기존 README의 사용 안내가 있으면 보완하고, 없으면 `TASK_ROOT/docs/hackathon/user-guide.md`에 작성해 README에서 찾을 수 있게 연결한다. 제출 형식·시험 규정이 제한하면 그 안에서 배치하며, 설명서 때문에 별도 프론트엔드를 추가하지 않는다.

- 실제 실행 명령과 확인된 접속 주소, 시작 화면과 대표 사용 순서.
- 화면별 목적, 버튼·입력 항목·기본값·필수 조건, 누른 뒤 바뀌는 데이터와 결과.
- 예시 입력 → 실제 확인된 결과, 잘못된 입력·중복·실패 시 동작. 미실행 예시는 예상 동작으로 표시.
- 결과 지표의 뜻·계산법·단위·비교 기준·해석 주의점. 계획한 목표와 실제 측정값을 분리.
- 구현됨·검증됨·미검증·미구현을 구분하고 제약·다음 개선을 표시.
- API 과제라면 화면 대신 실제 메서드·경로·요청/응답 예시·오류와 호출 순서를 설명.

설명서의 대표 흐름을 실제로 따라 확인하고 코드·문서 불일치는 고치거나 미검증으로 남긴다. 기능 설명서는 구현 증거를 설명하는 자료이지 공식 평가 기준을 임의로 만드는 문서가 아니다.

## 제출 문서 완료 후: 최종 요약

제출 문서와 기능 사용 안내를 정리한 뒤, 최종 제출 전에 **최종 요약**이라는 제목의 간결한 결과 보고서를 한 번에 보여 준다. 질문·답변이나 시험 대비 자료 형식이 아니라 무엇을 해결했고, 어떻게 구현·검증했으며, 누가 어떤 역할을 했는지 자연스럽게 설명한다. 설계 단계의 10문항 퀴즈는 반복하지 않는다. 과거 후기·캡처를 고정 출제 문항이나 공식 평가 기준으로 단정하지 않으며, 제공되지 않은 자료를 읽었다고 주장하지 않는다.

### 실제 근거를 읽고 반드시 짚을 내용

먼저 실제 코드·테스트·실행 기록과 계획의 차이를 확인한다. 각 항목을 `설명 요점 / 파일·함수 또는 모듈 / 관련 테스트·실제 결과 / 한계`로 연결한다. 계획 문장만으로 구현을 설명하지 않는다.

1. **알고리즘 원리와 선택 이유:** 입력을 어떤 순서·조건·기준으로 처리하는지, 왜 이 방법을 골랐는지, 대안과의 차이·장단점. 실제 사용하지 않은 알고리즘·최적화·성능을 덧붙이지 않는다.
2. **핵심 로직:** 대표 입력 한 건이 결과가 되기까지의 분기·계산·상태 변화, 성공 조건과 예외. 목표 지표와 실제 로직이 연결되는지 확인한다.
3. **백엔드 모듈 책임과 데이터 흐름:** 요청 수신 → 검증 → 업무 처리 → 저장/외부 호출 → 응답에서 실제 존재하는 모듈·함수의 역할과 경계를 설명한다. 백엔드가 없다면 해당 없음을 밝히고 실제 구조를 설명한다. 존재하지 않는 계층을 만들어 말하지 않는다.
4. **예상 장애와 대응:** 이 과제에 중요한 입력 실패·외부 연동 실패·중복/동시 요청·재시작 등 발생 조건, 탐지 방법, 데이터 영향, 현재 처리와 추가로 필요한 대응을 구분한다. 재시도·롤백·복구가 없는 경우 구현된 것처럼 쓰지 않는다.
5. **데이터 오류 확인·처리 책임:** 누락·형식/범위 오류·중복·업무상 모순을 어느 지점에서 검출하고 누가/어느 모듈이 거절·기록·정정·재처리하는지, 사용자에게 무엇을 알리는지 설명한다. 자동 처리와 사람의 확인이 필요한 부분, 책임이 아직 정해지지 않은 부분을 구분한다.
6. **AI 협업 기록:** 사용자가 정의·선택·수정한 내용, AI가 제안·작성한 내용, 사용자가 검토한 점, 오류를 발견·보완·검증한 과정을 실제 대화·findings·progress에 근거해 설명한다. 남아 있지 않은 대화나 검토·테스트를 지어내지 않는다.

각 항목을 검토하고, 관련 없음도 이유와 함께 표시한다. 모든 주장에 구현/미구현과 검증/미검증을 구분하고, 실패·한계·향후 계획을 숨기지 않는다. 설명 중 결함을 찾으면 기존 개발→검증 절차로 처리하고 산출물·설명을 갱신한다. 시간 부족을 이유로 검증되지 않은 설명으로 덮지 않는다.

### 간결한 결과 보고서 구성

위 필수 점검 내용을 아래 흐름에 자연스럽게 포함한다. 긴 문답 목록이나 서술형 대비라는 제목은 쓰지 않는다. 각 부분은 짧은 문단이나 핵심 bullet로 정리하고 파일·함수/모듈·테스트 근거는 필요한 곳에 간단히 붙인다. 별도 파일이 요구되지 않으면 대화에서 보여 주고, 기존 결과 보고서가 있으면 중복 문서 대신 그 요약을 보완한다.

- **해결한 문제와 결과:** 대상 사용자의 문제, 목표·핵심 범위, 실제 완성된 기능과 확인된 결과. 목표치와 실측치를 구분한다.
- **테스트 데이터 기반 최종 성능 결과:** 실제 실행한 테스트 데이터의 출처·종류(실제/샘플/합성)·표본 수·조건과 결과 수치를 함께 적는다. 과제에 맞는 지표의 계산식·단위·분모·측정 방법을 밝히고, 속도·정확도 등은 실제 측정한 경우에만 보고한다. 비교 가능한 기준선이 있을 때만 같은 조건의 전후 수치와 차이를 제시한다. 기준선이 없으면 개선율을 만들지 않고, 미실행은 미측정으로 표시한다. 작은 테스트 데이터의 결과를 실무 전체 효과로 일반화하거나 시간 단축·정확도 향상을 추정해 실측처럼 쓰지 않는다. 표본·환경·데이터 편향 등의 한계도 짧게 덧붙인다.
- **구현 방식과 판단:** 알고리즘·처리 순서와 선택 이유, 주요 모듈의 책임·데이터 흐름, 선택한 대안의 장단점. 필요한 경우 입력 한 건으로 쉽게 설명한다.
- **안정성과 검증:** 예상 장애·데이터 오류를 어디서 탐지하고 누가/어떤 모듈이 처리하는지, 실제 수행한 정상·예외 테스트와 결과. 구현된 대응과 향후 대응을 분리한다.
- **사용자와 AI의 역할:** 사용자 역할과 AI 역할을 별도로 표시한다. 문제 정의·우선순위·설계 결정·코드 작성·검토·검증 각각에서 실제로 누가 무엇을 했는지 근거대로 적는다. AI가 제안하고 사용자가 선택했다면 두 행동을 구분하고, 공동 논의는 각자의 기여를 밝힌다. 사용자에게 모든 판단·검증을 했다고 자동 귀속하거나 AI가 전부 수행했다고 쓰지 않는다. 기록이 부족한 기여는 확인 불가로 표시한다.
- **한계와 다음 개선:** 미구현·미검증·실패·남은 위험과 우선 개선점을 짧게 정리한다.

사용자는 제출 전에 이 요약을 읽고 확인한다. 추가 객관식 퀴즈·사용자 직접 응답·반복 연습을 필수 절차로 요구하지 않는다. 이해하기 어렵거나 사실과 다른 부분을 사용자가 짚으면 해당 내용만 보완한다. 이 정리를 사용자가 실제로 이해·검증했다는 증거로 취급하지 않는다.

정리한 항목·코드 근거·불명확한 부분은 기존 progress에 짧게 기록한다. 새 보고서를 공식 필수 제출물이라고 단정하지 않는다. 이 정리는 **제출 전 허용된 준비 단계**이며, 시험 서술형 단계의 AI·외부 자료 사용이 허용된다고 가정하지 않는다. 실제 서술형에 들어가면 해당 규정을 확인하고 금지된 지원은 하지 않는다.

135–165분 산출물 예산 안에서 문서 작성 뒤 이 점검 시간을 미리 확보하고, 최종 검증·제출 시간을 보존한다. 시간이 부족하면 AI가 남은 필수 항목·단축안·위험을 제시하고 사용자에게 우선순위와 진행 방식을 선택받는다. 조용히 생략하거나 완료로 표시하지 않는다. 최종 제출 뒤 별도 연습 시간이 자동 제공된다고 가정하지 않는다.

## 제출 전 확인

- 요구 산출물의 존재·경로·형식·파일명, 링크 대상과 접근 가능 여부를 확인한다. 접근을 검사하지 못한 링크는 미확인으로 표시한다.
- 최종 smoke test는 핵심 사용자 흐름을 대상으로 실제 수행한다. 전체 테스트와 동일하다고 표현하지 않는다. 실행 불가·실패·미검증과 남은 위험을 기록한다.
- 구현 완료·검증 통과·산출물 준비·제출 완료를 구분한다. 문서를 읽거나 문서 링크를 확인한 것은 실행 테스트 통과의 근거가 아니다.
- 최종 제출 조작은 시험 안내와 사용자의 승인 범위에 따른다. 대상·내용·행위가 이미 명시적으로 승인되어 있으면 반복 확인하지 않는다. 없으면 검토 가능한 제출 묶음과 필요한 조작을 제시하고 승인받는다. 도구 권한도 별도로 준수한다.
- 실제 제출 후 결과 화면·접수 상태·제출 시각 등 확인 가능한 증거만 기록한다. 조작할 수 없거나 결과를 확인할 수 없으면 제출 준비 또는 결과 미확인으로 보고한다. 준비만 끝난 상태를 제출 완료라고 쓰지 않는다.

## 출력

과제 지정 산출물과 짧은 인계 보고를 제공한다. 보고에는 생성·수정 경로, 실제 검증 결과, 실패·미검증·한계, 제출 상태와 다음 필요한 행동을 담는다. 추정이나 자기 검토를 측정 결과·독립 검토라고 쓰지 않는다.
