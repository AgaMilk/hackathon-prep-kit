# 설계와 이해 점검

[AGENTS.md](../AGENTS.md)의 승인·시간·기록 규칙을 보완한다. 과제 규정이 우선이며 완료한 setup은 반복하지 않는다. 계획·근거·진행은 setup에서 매핑한 기존 문서에 기록한다. 아래 기본 경로가 실제와 다르면 사용 중인 경로로 바꾸고, 파일이 없으면 현재 세션이 해당 단계의 내용을 먼저 작성한다. 리뷰 세션에 없는 파일을 읽었다고 가정하지 않는다.

## 1. AI가 먼저 설명하고 선택을 돕기

사용자에게 질문부터 나열하지 말고 자료를 읽어 다음을 짧게 설명한다. 긴 기술 용어보다 실제 사용자 한 명의 입력 → 처리 → 결과 예시를 든다.

- 누구의 어떤 불편을 줄이며, 완성하면 무엇이 달라지는가? 핵심 기능과 제외 범위는 무엇인가?
- 데이터 한 건의 단위·중복/조합 기준·상태 변화는 무엇인가? 정상 흐름 외에 빈 값·한계값·중복·동시 요청 등 이 과제에 중요한 예외는 무엇인가?
- 공식 평가 기준이 있으면 기능·검증에 어떻게 연결되는가? 없다면 무엇을 성공으로 볼 것인가?
- 지표별 계산법·단위·대상 범위·기준값·데이터 출처·측정 방법은 무엇인가? 계획 목표, 예시 데이터, 실측 결과를 구분한다.
- 목표끼리 충돌하지 않는가? 예: 버스 탑승률을 높이면서 탑승자의 시간을 줄일 때, 탑승 대기·차내 시간 중 무엇을 뜻하는지와 차량 비용·미탑승 허용 여부를 먼저 구분한다. 평균 개선이 일부 이용자의 과도한 지연을 감추는지도 점검한다. 이 예시의 답을 다른 과제에 강제하지 않는다.

발견한 누락·모순·실패 위험을 AI가 먼저 알리고 해결 대안·장단점·추천 이유를 제시한다. 공식 기준에 없는 핵심 지표의 우선순위·가중치·허용 한계는 사용자 선택 사항이다. 필요한 결정을 중요한 것부터 2~3개로 묶어 묻는다. 정해지지 않은 숫자·업무 규칙을 임의로 채우지 않는다. 현업 확인이 필요한 사실과 사용자가 선택할 방향을 구분한다.

`implementation-plan.md`에 목표/선택한 지표/핵심 흐름/범위/입출력/예외/검증 기준/미결사항을 적고, `findings.md`에 사실·출처·가정·결정 이유를 구분해 남긴다. 문서 길이보다 사용자가 다음 결정을 이해할 수 있는지가 우선이다.

## 2. 1차 설계 뒤 별도 세션 리뷰

AI가 실제 문서 경로를 넣어 아래 한 문단 요청을 만들어 준다. 사용자가 같은 프로젝트의 별도 세션을 직접 열어 복사한다. 별도 파일 첨부나 설계 요약을 다시 만들게 하지 않는다.

> 현재 과제의 적용 지침과 docs/hackathon/progress.md에서 실제 문서 경로를 확인한 뒤 docs/hackathon/implementation-plan.md와 docs/hackathon/findings.md를 읽어 줘. 1차 설계의 목표·지표 충돌, 빠진 요구사항·예외, 데이터 단위, 검증 가능성을 독립적으로 검토하고 중요도·근거·대안·사용자 결정이 필요한 사항을 짧게 정리해 줘. 파일 수정·구현·setup 재실행은 하지 마.

기본 경로가 아니면 위 요청의 모든 경로를 실제 경로로 치환한다. 리뷰 결과를 사용자가 주 세션에 전달하면 AI는 수용/보류할 이유를 설명하고, 핵심 결정은 사용자에게 요청한다. reviewer의 제안만으로 사용자 선택을 확정하지 않는다. 실제 리뷰 결과와 반영 상태를 progress에 남긴다. 자동 통신·감시·무한 리뷰는 하지 않는다.

## 3. 쉬운 설명 후 10문항 퀴즈

리뷰가 반영된 현재 설계의 목적·핵심 흐름·판단 기준을 간단히 설명한 뒤 객관식 10문항을 **한 번에 하나씩** 낸다. 질문마다 진행 번호(예: 3/10)를 표시한다.

- 목표·사용 흐름·데이터/지표·업무 규칙·예외·범위에서 과제에 중요한 내용으로 배분한다. 고정 문항 수 할당이나 기술 상식 시험으로 만들지 않는다.
- 실제 현재 설계와 구체적인 상황으로 묻고 짧은 3~4개 선택지를 준다. 아직 미결인 업무 결정을 정답으로 단정하지 않는다.
- 사용자가 답하면 정답 여부와 이유를 짧게 설명하고 다음 질문으로 넘어간다. 같은 질문을 다시 풀게 하지 않는다. AI의 설계 자체가 잘못됐을 가능성도 확인한다.
- 사용자의 첨언·이견은 문항 번호와 함께 progress에 모아 두고 퀴즈 후 한꺼번에 검토한다. 사소한 의견마다 설계를 즉시 바꿔 퀴즈 흐름을 끊지 않는다.
- 다만 남은 질문의 전제를 무너뜨리는 모순·규정 위반 가능성은 즉시 알리고 해당 부분의 결정을 요청한다. 해결 후 남은 문항을 조정하며 이미 끝낸 문항을 반복하지 않는다.

끝나면 단순 이해 차이 / 설계 결함 / 현업 확인 필요를 나누고 모인 의견과 수정안을 제시한다. 점수나 사용자의 정답 수를 설계 품질·수상 가능성으로 해석하지 않는다. 합의된 수정은 계획과 근거 문서에 반영하고, 보류 사항·변경 이유·영향받는 검증 기준을 progress에 기록한다.

## 4. 수정 설계의 2차 리뷰와 변경점 확인

실제 경로를 넣어 두 번째 짧은 요청을 제공한다.

> 현재 과제의 적용 지침과 docs/hackathon/progress.md의 퀴즈 의견·변경 기록을 확인하고 docs/hackathon/implementation-plan.md와 docs/hackathon/findings.md의 최신 설계를 검토해 줘. 의견이 제대로 반영됐는지, 변경으로 새로운 충돌·예외 누락·지표 문제가 생겼는지 확인하고 남은 위험과 사용자 결정 사항만 정리해 줘. 파일 수정·구현·setup 재실행은 하지 마.

실제 리뷰 결과를 받아 변경 전 → 변경 후 → 이유 → 기능/검증 영향만 짧게 보여 준다. 전 문항을 다시 묻지 않는다. 핵심 선택·미결사항이 해소되면 AGENTS.md의 기존 묶음 승인에 포함해 구현으로 넘어간다. 이미 승인된 부분은 반복 승인받지 않으며, 이후 실질적 방향 변경만 재승인받는다. 독립 리뷰를 하지 못했다면 미실시로 기록하고 대안을 제시하며 사용자에게 진행 방식을 선택받는다.

## 5. 구현 중 방향 유지와 시간

핵심 흐름이 동작하거나 설계가 바뀔 때 목표 → 구현한 기능 → 실제 검증 결과 → 남은 위험을 짧게 공유한다. 계획의 기대 수치를 실측처럼 보고하지 않는다. 목표·핵심 지표·범위가 바뀌면 변경 영향과 사용자 결정을 먼저 확인한다. 완료 단계에는 [delivery.md](delivery.md)에 따라 실제 기능 사용 안내를 만든다.

이 절차는 기본 15–45분 설계 예산 안에서 계획하며 시험의 실제 남은 시간에 맞춘다. 단계 시작·종료 때 시간을 확인하고 검증·산출물·제출 여유를 보존한다. 시간이 부족하면 AI가 리뷰 범위 축소·문항 축소·기능 축소 등 대안과 위험을 먼저 제시하되 사용자가 선택한다. 명시적인 지시 없이는 퀴즈를 생략하거나 핵심 지표를 대신 선택하지 않는다. 가정하고 진행하라는 지시가 있으면 허용 범위·가정·영향·확인 방법을 기록한다. 정해진 규정·권한을 넘는 가정은 하지 않는다.
